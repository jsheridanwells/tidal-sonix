# SPEC-002: Containerize the server and validate locally

## ADR

Decisions and rationale for this slice live in [`adr/ADR-002.md`](../adr/ADR-002.md). Read it before starting; do not restate it here.

## Specs

### Spec 1: `Program.cs` change

Strip the hardcoded URL from `app.Run`:

> **Code lives in reference.** C# block 1 of `reference/SPEC-002.md` ("Spec 1: `Program.cs` change"). Write it yourself first; open the reference only if stuck.
> Shape: `MapMcp()`

The single-line change is `app.Run("http://localhost:3001")` → `app.Run()`. ASP.NET Core now picks up the bind URL from:

1. `ASPNETCORE_URLS` environment variable (used by the container's base image, default `http://+:8080`), or
2. `Properties/launchSettings.json` (used by `dotnet run` locally — see Spec 2).

### Spec 2: `launchSettings.json` verification

`dotnet new web` should have created `src/TidalSonics.Server/Properties/launchSettings.json` with a profile that sets `applicationUrl` to some random localhost port. Edit the relevant profile to pin port 3001 so local `dotnet run` keeps the same URL it had in SPEC-001:

> **Code lives in reference.** config (JSON) block 2 of `reference/SPEC-002.md` ("Spec 2: `launchSettings.json` verification"). Write it yourself first; open the reference only if stuck.

Other profiles (`https`, `IIS Express`) generated by the template can be deleted or left; not used for our flow.

### Spec 3: `.dockerignore`

Create `.dockerignore` at the **repo root** (same directory as the Dockerfile will live):

> **Code lives in reference.** file contents block 3 of `reference/SPEC-002.md` ("Spec 3: `.dockerignore`"). Write it yourself first; open the reference only if stuck.

Tighter than strictly necessary, but cheap.

### Spec 4: `Dockerfile`

Multi-stage, placed at the repo root (`tidal-sonics/Dockerfile`):

> **Code lives in reference.** Dockerfile block 4 of `reference/SPEC-002.md` ("Spec 4: `Dockerfile`"). Write it yourself first; open the reference only if stuck.

Two layers to be aware of:

1. **Restore-before-copy** pattern. Copying only the `.csproj` first and running `dotnet restore` against it means the build cache can hold the package-restore layer until your dependencies actually change. Source-only edits skip the restore layer entirely on rebuilds.
2. **`--no-restore` on publish.** Avoids redoing restore work we just did one layer up.

The `# syntax=docker/dockerfile:1.7` directive is honored by both BuildKit and buildah (the engine podman build uses under the hood), so the Dockerfile remains portable.

### Spec 5: Local validation

After building and running:

```bash
podman build -t tidal-sonics-server:dev .
podman run --rm -p 3001:8080 --name tidal-sonics-dev tidal-sonics-server:dev
```

In a separate terminal:

```bash
npx @modelcontextprotocol/inspector
```

Connect to `http://localhost:3001` (with the same MCP path used in SPEC-001) over Streamable HTTP. Confirm `Hello` is listed, invoke with `{ "name": "Jeremy" }`, confirm response.

Then **stop the container** (`Ctrl+C` or `podman stop tidal-sonics-dev`) and run `dotnet run --project src/TidalSonics.Server` to confirm the non-container path still works on port 3001 too. Both paths green = slice done.

## Tasks

### Task 1: Modify `Program.cs`

Edit `src/TidalSonics.Server/Program.cs` to change `app.Run("http://localhost:3001")` to `app.Run()`. Commit: `refactor: source bind URL from configuration rather than hardcoding`.

### Task 2: Pin local dev port via `launchSettings.json`

Open `src/TidalSonics.Server/Properties/launchSettings.json`. Set `applicationUrl` to `http://localhost:3001` on the `http` profile. Delete extraneous profiles if you want. Run `dotnet run --project src/TidalSonics.Server`. Confirm it binds to 3001 (it should — same behavior as SPEC-001). Commit: `chore: pin local dev port to 3001 via launchSettings`.

### Task 3: Create `.dockerignore`

Create `tidal-sonics/.dockerignore` with the contents from Spec 3. Commit: `chore: add .dockerignore`.

### Task 4: Create the `Dockerfile`

Create `tidal-sonics/Dockerfile` with the contents from Spec 4. Commit: `feat: containerize server with multi-stage Dockerfile`.

### Task 5: Build the image

From the repo root:

```bash
podman build -t tidal-sonics-server:dev .
```

Confirm the build completes with no warnings. Inspect the image size:

```bash
podman images tidal-sonics-server
```

Should be on the order of a few hundred MB (Debian-based aspnet image isn't tiny). Note the size for comparison if you later try chiseled images.

### Task 6: Run the container and validate via Inspector

```bash
podman run --rm -p 3001:8080 --name tidal-sonics-dev tidal-sonics-server:dev
```

Confirm logs show the server listening on `http://[::]:8080` inside the container. In a second terminal run `npx @modelcontextprotocol/inspector`, connect to `http://localhost:3001`, confirm the `Hello` tool, invoke it, confirm the greeting.

### Task 7: Confirm non-container path still works

Stop the container. Run `dotnet run --project src/TidalSonics.Server`. Re-point Inspector at `http://localhost:3001`. Confirm same behavior. This proves the `Program.cs` change didn't regress the local dev workflow.

If all of the above pass, SPEC-002 is **Completed**. Update frontmatter `status` and `last_updated` and commit the spec.

## Notes

- **Why not just `dotnet publish /t:PublishContainer`?** .NET ships a built-in container publish target that can produce an image without a Dockerfile. Tempting and arguably cleaner. Skipping it deliberately: writing the Dockerfile by hand once is a useful learning exercise, and the explicit file is easier to reason about for the OAuth and Key Vault concerns coming later. If you'd rather use the built-in target, swap it in — none of the downstream specs depend on a hand-written Dockerfile.
- **Podman specifics.** On macOS / Windows, podman runs containers inside a managed Linux VM (`podman machine`). If you haven't already, `podman machine init && podman machine start` is the one-time setup; after that, the `podman build` / `podman run` commands above behave the same as on a Linux host. Rootless mode is the default — fine for everything in this slice. Port mapping via `-p 3001:8080` works identically to docker.
- **Image size benchmark.** Standard aspnet:10.0 base is ~220 MB; final published image will likely be ~250–280 MB. Chiseled `aspnet:10.0-noble-chiseled` runs around 110 MB. Worth noting only because it's the first thing you'll want to optimize when the slow Container Apps pull starts annoying you.
- **`MapMcp` path consistency.** Whatever path you settled on in SPEC-001 (default or explicit `/mcp`) carries forward unchanged here — the container doesn't change the routing.
