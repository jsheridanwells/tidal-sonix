# ADR-008: `search_tracks` tool against TIDAL Catalog v2

Spec: [`specs/SPEC-008.md`](../specs/SPEC-008.md)

This slice puts real TIDAL data behind a tool for the first time. Decisions:

- **TIDAL Web API v2 at `https://openapi.tidal.com/v2`.** JSON:API-shaped responses. `Accept: application/vnd.api+json` on every request. The v1 catalog API still exists but is being phased out in favor of v2.
- **Client-credentials OAuth flow for SPEC-008.** Search hits catalog metadata, not user data — client credentials is the right grant. Endpoint: `POST https://auth.tidal.com/v1/oauth2/token` with `Authorization: Basic base64(client_id:client_secret)` and `grant_type=client_credentials`. Tokens last 24 hours.
- **Playlist operations (SPEC-009 onward) require a user-context token.** Different grant (authorization_code with PKCE), different scope, separate flow. SPEC-009 will introduce a parallel "user-context hardcoded token" path; for now, we don't need it. Don't try to unify the two prematurely — they really are different grants with different lifecycles.
- **`TidalTokenProvider` is a singleton with a `SemaphoreSlim`-guarded cache.** Holds the current access token plus its expiry; mints lazily on first call, re-mints if expired or within a 60-second leeway window. Re-mints on 401 from the catalog API (defensive — clock skew, token revocation).
- **`TidalCatalogClient` is a typed `HttpClient` via `IHttpClientFactory`.** Named-client registration with `BaseAddress` and default JSON:API headers. A `DelegatingHandler` adds the Bearer token from `TidalTokenProvider` to every request and retries once on 401 after forcing a token refresh.
- **Single endpoint per search.** `GET /v2/searchresults/{urlencoded-query}?countryCode={cc}&include=tracks,tracks.artists`. The `include` parameter sideloads track and artist entities in the `included` array so we don't fan out to `/v2/tracks/{id}` per result (which would hit TIDAL's surprisingly tight rate limit — ~2 req / 10s on the developer tier).
- **`countryCode` defaults to `"US"`.** Single-user tool, configurable via `appsettings.json` but pinned for our case. Required parameter on the TIDAL endpoint — not optional.
- **JSON:API parsing kept narrow.** We don't try to model the full JSON:API spec. We deserialize just enough: the top-level `data.relationships.tracks.data` array (an ordered list of `{type,id}` refs) and the `included` array as a flat `List<IncludedResource>`. Track lookup is by `(type, id)` against `included`; artist names follow the track's `relationships.artists.data` refs into the same flat list.
- **Tool returns the top N tracks in TIDAL's order.** No client-side reranking. Default `limit = 10`; the tool clamps to a max of 25. We don't paginate — the LLM rarely benefits from more than 10 candidates, and one search request keeps us inside the rate limit comfortably.
- **Tool description carries explicit disambiguation guidance.** The whole point of this tool over "just pick the first hit" is to let me sanity-check matches. The description tells the model to surface multiple candidates and ask before adding to a playlist. This is load-bearing prompt engineering — invest in it now since later tools will rely on the LLM having chosen good track IDs.
- **`[Authorize]` on the tool**, same scheme as `Hello` (SPEC-007). claude.ai must present a valid JWT to call it.
- **No tests this slice.** Keeping with the project's "tests when there's a reason" stance. The TIDAL API is the integration point worth testing eventually; mocking JSON:API responses is its own effort. Flagged as future work.

Out of scope: user-context TIDAL tokens (SPEC-009), refresh-token handling for TIDAL (SPEC-012 has the bootstrap for that), pagination, fuzzy matching / reranking, ISRC lookup, album / artist search variants, caching search results.
