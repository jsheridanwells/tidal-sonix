# ADR-012: `/connect-tidal` bootstrap route

Spec: [`specs/SPEC-012.md`](../specs/SPEC-012.md)

**Last post-MVP slice.** SPEC-010 finished the functional MVP; SPEC-011 unified secret storage; this slice removes the last bit of operational drag — the manual shell script for TIDAL OAuth bootstrap. After this, re-authenticating TIDAL is a browser visit, and the application is fully self-contained.

Decisions:

- **Replace `tidal-user-bootstrap.sh` with three server routes:** `GET /connect-tidal` initiates the flow, `GET /tidal-callback` receives the code and exchanges for tokens, `GET /tidal-connected` (and `GET /tidal-error`) terminate the flow with a small HTML page. The script stays in the repo as a fallback for first-time local-only bootstrapping where you can't yet reach the server externally, but normal operations no longer touch it.
- **`/connect-tidal` is cookie-auth gated.** Same scheme as `/me` (SPEC-006). An unauthenticated visit bounces through Google sign-in first; the allow-list of one means only you can initiate the TIDAL flow. Important: this protects the TIDAL credentials from anyone who happens to know the URL.
- **PKCE state lives in an in-memory store keyed by the `state` parameter.** Same shape as `AuthorizationCodeStore` from SPEC-007: `ConcurrentDictionary<string, PkceState>`, 5-minute TTL, single-replica-safe. The code_verifier needs to survive the redirect to TIDAL and back; in-memory is the simplest correct option for our `max-replicas 1` deployment.
- **The state key is the OAuth `state` parameter itself.** Random, server-generated, returned in the callback URL. Doubles as CSRF protection — we reject any callback whose state isn't in the dict (or isn't recent).
- **`ITidalSecretStore` extended with `UpdateUserTokensAsync(access, refresh)`.** Single call to update both secrets atomically (in spirit — KV doesn't have a transaction primitive across secrets, but a single method ensures both writes are issued together). The no-op local impl logs the `dotnet user-secrets set` commands so you can still close the loop on a local-only setup if you ever want to.
- **`TidalUserTokenProvider` gets a `Reload(accessToken, refreshToken, expiresAt)` method.** After the callback handler successfully exchanges code for tokens and writes them to KV, it calls `Reload` so the running provider picks up the new state without a process restart. This is the load-bearing bit that makes "re-auth via browser" actually mean "the server is live and working again immediately."
- **TIDAL redirect URIs:** add `https://<tunnel-id>-3001.<region>.devtunnels.ms/tidal-callback` and `https://<app-fqdn>/tidal-callback` to the TIDAL Developer Portal. The localhost:8888 entry from SPEC-009 can stay (script fallback) or be removed.
- **No DCR.** Same pre-registered TIDAL client as SPEC-008/009 — we own both sides of this OAuth relationship, no dynamic registration needed.
- **Scope unchanged: `playlists.read playlists.write`.** Same as SPEC-009. If the TIDAL Developer Portal exposed more granular scopes we wanted, we'd narrow further; doesn't right now.
- **The success page is just HTML.** A modest "Connected to TIDAL. You can close this tab" page. No fancy SPA, no redirect back to claude.ai — just terminal confirmation that the flow worked. A link back to `/me` for sanity if you want it.
- **Local dev path stays via the tunnel.** Pointing `http://localhost:3001/connect-tidal` at TIDAL doesn't work (TIDAL requires HTTPS for redirect URIs in most cases, and even if they allow `http://localhost`, the local server isn't reachable from TIDAL anyway). Use the dev tunnel URL for local-but-real-OAuth flows. The SPEC-009 script remains the truly-offline path for when even the tunnel is too much.
- **Error responses are HTML, not JSON.** This is a browser flow; users see them. Include enough information to debug (the error code, a short description), enough to not leak (no full stack traces, no secrets), and a link to retry.

Out of scope: token revocation endpoint on TIDAL (TIDAL provides one; we don't expose it), automated re-auth via a scheduled job when refresh nears expiry (cookie auth + manual visit is fine for personal use), webhook notifications when tokens rotate.
