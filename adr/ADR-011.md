# ADR-011: Migrate secrets to Azure Key Vault

Spec: [`specs/SPEC-011.md`](../specs/SPEC-011.md)

**Post-MVP slice.** SPEC-010 was the functional boundary — the project does the thing it was built to do. This slice (and SPEC-012) are production-hygiene polish. The two motivations:

1. **Single source of truth for production secrets.** Right now they're scattered across `az containerapp secret set` calls from three different specs. Adding a new secret means remembering which CLI dance applies. Key Vault gives us versioning, access auditing, and one place to look.
2. **Closes the SPEC-009 refresh-token friction.** When TIDAL rotates the user refresh token, SPEC-009 logs a warning with the new value and trusts you to update user-secrets manually. After this slice, the rotated token is persisted to Key Vault automatically — so process restart no longer means "was the refresh token rotated since I last updated user-secrets?"

Decisions:

- **Single Key Vault instance.** Standard SKU is fine; Premium adds HSM-backed keys, which we don't need (we store the RSA private key as a Secret, not a Key — see below). Same region as the rest of the resources, same resource group.
- **RBAC, not access policies.** Modern, easier to reason about. Grants survive the inevitable forgetting-then-remembering cycle better than per-secret access policies. The two roles in play:
  - **`Key Vault Secrets Officer`** on the UAMI — read AND write. Write is needed for refresh-token rotation persistence.
  - **You (interactively, for setup)** get `Key Vault Secrets Officer` on yourself via the Azure CLI's currently-signed-in account.
- **RSA signing key stored as a Secret, not a Key.** Key Vault has a separate "Keys" feature where the private key never leaves the vault — sign operations happen inside KV via API call. That's the more rigorous pattern, but it requires changing our JWT signing code from "synchronous in-process RSA" to "async call to KV per signature." Big enough change that it deserves its own slice; not in this one's scope. Storing the PEM as a Secret keeps signing in-process and gets us the auditing + rotation benefits of KV without the architectural shift.
- **Secret naming uses the `--` separator.** Key Vault doesn't allow `:` in secret names. The `Azure.Extensions.AspNetCore.Configuration.Secrets` package converts `--` to `:` automatically when loading into `IConfiguration`. So `Google--ClientSecret` in KV becomes `Google:ClientSecret` in code — no app-side changes to existing config reads.
- **All secrets move, not just the truly-secret ones.** Strictly, `Google:ClientId`, `OAuth:Clients:0:ClientId`, `Tidal:ClientId` are public-ish identifiers, not secrets. They could stay in `appsettings.json` or env vars. We put them in KV anyway, for a simpler mental model: in production, **all** config that varies between environments lives in KV. The non-secret stuff (port numbers, lifetime tunables) stays in `appsettings.json`.
- **`DefaultAzureCredential` for authentication.** Picks up the UAMI in Container Apps automatically. Locally, it'd fall back to Azure CLI / VS / VS Code creds — but we don't need local KV access since user-secrets covers local dev.
- **KV configuration source registered conditionally.** Only when the `KEY_VAULT_URI` env var is present. Local dev (no env var) → KV provider isn't loaded, user-secrets continues to be the source. Prod (`KEY_VAULT_URI` set) → KV provider loads, user-secrets is irrelevant (and isn't present in the container anyway).
- **`TidalSecretStore` service for write-back.** Thin wrapper around `SecretClient` exposing a single `UpdateAsync(secretName, value)` method. `TidalUserTokenProvider` calls it when it sees a rotated refresh token. Local dev: the env var isn't set, the service isn't registered, the rotation-warning-only path from SPEC-009 stays in effect.
- **Remove Container Apps native secrets after migration.** Cleanup task at the end. The CA secret store and KV both holding the same values is a recipe for drift; KV alone is the source going forward.
- **No automated rotation of OAuth signing key, Google client secret, or TIDAL client credentials.** Manual rotation via `az keyvault secret set` works for now. KV-native rotation policies are a future slice if the project ever cares about that level of hygiene.

Out of scope: KV-Keys feature for signing (signing key stays a Secret), KV-managed rotation policies, KV firewall / private endpoint configuration, custom secret versioning logic, secret-change notification, removing user-secrets locally (it's still the dev source).
