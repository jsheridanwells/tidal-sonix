# ADR-009: `find_playlist_by_name` and `create_playlist` tools

Spec: [`specs/SPEC-009.md`](../specs/SPEC-009.md)

This slice introduces a second TIDAL token path for the playlist endpoints, which require a user-context grant (`authorization_code` + PKCE) — client_credentials is explicitly not supported for them. Two tools land: `find_playlist_by_name` for idempotency, and `create_playlist` for the actual write. Decisions:

- **Authorization Code + PKCE grant for user context.** TIDAL's v2 playlist endpoints require a user-context access token; this is the only grant that supplies one. The two grants are kept fully separate from SPEC-008's client_credentials — different token provider, different `HttpClient`, different DelegatingHandler. Resist the urge to unify; their refresh paths and failure modes really do differ.
- **One-time manual bootstrap, not yet automated.** SPEC-012 implements `/connect-tidal` as a route on our running server. For now, a tiny `scripts/tidal-user-bootstrap.sh` walks through the PKCE flow on the developer's machine, opens the TIDAL authorize URL in a browser, prompts for the redirect URL after sign-in, exchanges the code, and prints `dotnet user-secrets set` commands. Idempotent — re-run only when refresh fails.
- **Bootstrap redirect URI: `http://localhost:8888/tidal-bootstrap-callback`.** TIDAL pre-registration only. Nothing listens on 8888 during the flow — we capture the code from the browser URL bar after the redirect-error page. Adding a real listener is one more moving part for one extra minute of friction; skip it.
- **Scopes requested: `playlists.read playlists.write`.** Confirmed working on the v2 spec per TIDAL's developer forum threads (the older `r_usr` scope doesn't work with v2 endpoints — distinct surface). Add `user.read` if endpoint shape requires user ID lookup (verify against the OpenAPI spec; flagged in Notes).
- **`TidalUserTokenProvider` mirrors `TidalTokenProvider` but uses `refresh_token` grant.** Same `SemaphoreSlim`-guarded double-checked cache pattern. On 401 from the catalog API, forces a refresh. On refresh failure (refresh_token revoked or expired), throws a typed exception — `TidalAuthExpiredException` — surfacing through to the tool's response as a structured error telling the user to re-run the bootstrap.
- **Refresh-token rotation: in-memory only this slice.** If TIDAL rotates the refresh_token on each refresh (OAuth 2.1 best practice for public clients; optional for confidential — TIDAL's behavior verified empirically), the new value lives only in process memory. On process restart, we fall back to whatever's in user-secrets, which may be stale. Mitigation: log a warning with the new refresh_token whenever rotation is observed, so you can manually update secrets if needed. SPEC-011's Key Vault migration adds persistence; SPEC-012's bootstrap automation closes the loop fully.
- **Two new MCP tools, one new client.**
  - `TidalPlaylistClient` typed `HttpClient`, separate from `TidalCatalogClient`, using the user-context auth handler. Same JSON:API decoding infrastructure from SPEC-008.
  - `PlaylistTool` class with two `[McpServerTool]` methods.
- **`find_playlist_by_name` returns a list, not an Option.** Empty list when no match. Plural return is more honest about reality — playlists can share names — and lets the LLM disambiguate with the user before writing.
- **`create_playlist` is unconditional.** It does NOT check for existing playlists with the same name first. The LLM is responsible for calling `find_playlist_by_name` first if it wants idempotency. Splitting the two operations keeps each tool single-purpose and lets the LLM compose them; bundling the find-then-create logic into one tool removes the chance to ask the user "you already have a playlist with this name — add to it, or create a duplicate?".
- **Tool descriptions explicitly cover the idempotency flow.** Both tools' descriptions reference each other: `create_playlist`'s description tells the model to call `find_playlist_by_name` first when the user's intent is "add to playlist X" rather than "create a new playlist."
- **`[Authorize]` on tools, same JWT scheme as SPEC-007 / 008.**
- **No `add_tracks_to_playlist` this slice.** That's SPEC-010 — the moment all three operations are needed for the full end-to-end "build playlist from chat" flow. Keeping the playlist creation slice tight makes it easier to debug the user-context token mechanics in isolation.
- **`country_code` parameter: not present on playlist endpoints** (user-context implies a country already on the TIDAL account). Catalog endpoints in SPEC-008 still use the configured default. Don't propagate the parameter unnecessarily.
- **Some endpoint paths in this spec are best-effort.** TIDAL's v2 user-playlist surface is documented behind `https://developer.tidal.com/apiref?spec=user-playlist-v2`, which I couldn't fully scrape in research. The Spec sections below give the most likely paths based on JSON:API conventions and discussion-forum snippets; Task 3 has you cross-check against the official spec before writing code.

Out of scope: `add_tracks_to_playlist` (SPEC-010), deleting / updating playlists, listing all playlists, folder support, the full `/connect-tidal` automated flow (SPEC-012), persisting rotated refresh tokens (SPEC-011 helps; SPEC-012 finishes it).
