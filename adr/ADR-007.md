# ADR-007: OAuth Authorization Server and JWT-protected MCP endpoint

Spec: [`specs/SPEC-007.md`](../specs/SPEC-007.md)

This is the largest slice in the project, deliberately. The work is one axis — turn the server into an OAuth 2.1 AS that mints JWTs, then protect `/mcp` with those JWTs, then reconfigure claude.ai to use it — but the axis is big enough that you may want to commit twice mid-slice. That's fine; the success criteria are end-to-end, but the sub-specs build linearly so partial work is recoverable.

Decisions:

- **Pre-registered confidential client, not Dynamic Client Registration.** claude.ai's connector "Advanced settings" supports a manual `client_id` + `client_secret`, which lets us skip implementing `/register` (RFC 7591) in this slice. DCR is a strict win for multi-client situations and a worthwhile optional follow-up; not blocking for personal use. The pre-registered client is hardcoded in config: a `client_id` (something opaque like `claude-ai-prod`), a `client_secret` (random, in user-secrets), and a list of allowed redirect URIs (`https://claude.ai/api/mcp/auth_callback`, `https://claude.com/api/mcp/auth_callback`).
- **RSA 2048 signing key.** Generated once with `openssl` or `dotnet`, private key PEM stored in user-secrets (Key Vault in SPEC-010). We use the private key directly for both signing and verification — no JWKS endpoint yet. JWKS is the right shape for a real AS that serves many resource servers, but for a server that validates its own tokens in-process it's unnecessary overhead and adds a moving part. Defer.
- **In-memory authorization code store.** Codes are short-lived (60 seconds), one-use, and single-replica (Container Apps `max-replicas 1` from SPEC-003 means no cross-replica state). A `ConcurrentDictionary<string, AuthCode>` is correct here. Persistent storage is overkill for a personal tool.
- **Access token TTL: 24 hours. No refresh tokens this slice.** If a token expires while claude.ai is using it, claude.ai re-runs the OAuth flow. Cookie auth from SPEC-006 carries forward (14-day default), so re-running the flow is silent for the user as long as the Google cookie is still valid. Refresh-token rotation per OAuth 2.1 is a worthwhile polish item; flagged in Notes.
- **PKCE with S256 mandatory.** Per the MCP authorization spec and confirmed by reading claude.ai's actual flow, every `/authorize` request from claude.ai includes `code_challenge` with `code_challenge_method=S256`. AS metadata must advertise this; `/token` must verify the verifier.
- **Resource Indicators (RFC 8707) supported.** claude.ai sends `resource` on `/authorize` and `/token`. We bind the issued JWT's `aud` claim to that value. This protects against token replay across resource servers — relevant once you have more than one MCP server, harmless and correct now.
- **Dynamic issuer from request.** The server runs at three URLs over its lifetime: `http://localhost:3001` (local dev), the dev tunnel hostname (outer loop), and `https://<app-fqdn>` (prod). PRM `resource`, AS `issuer`, and JWT `iss` claim all need to match whichever URL claude.ai connected to. We register `UseForwardedHeaders` so `Request.Scheme`/`Request.Host` reflect the public URL behind Container Apps' / dev tunnels' / Google's proxies, then derive the issuer from `Request.GetEncodedUrl()` minus path.
- **Single scope: `mcp:tools`.** No scope granularity within the server. claude.ai requests this scope; we issue it. A more elaborate server might split read/write/admin; we don't.
- **Cookie auth from SPEC-006 is the gate for `/authorize`.** If `/authorize` hits with no cookie, we trigger the Google challenge (same as SPEC-006's `/signin`) with a redirect back to the original `/authorize` URL preserving the query string. After Google sign-in and allow-list pass, the cookie is set, `/authorize` re-runs with the cookie, code is issued. This is the entire point of building Google sign-in first.
- **`/mcp` protected with `Microsoft.AspNetCore.Authentication.JwtBearer` + `[Authorize]`.** The `McpAuthenticationHandler` from `ModelContextProtocol.AspNetCore` automatically adds `WWW-Authenticate: Bearer ... resource_metadata="..."` on 401, which is what triggers claude.ai's discovery flow. We call `.AddAuthorizationFilters()` on the McpServer builder and decorate `Hello` with `[Authorize]`.
- **Client secret comparison is constant-time on cleartext from user-secrets.** Not "store only the hash" — that's the production-grade pattern (PBKDF2 / bcrypt) and worth doing eventually, but for a single-client, single-user secret that's already protected by being in user-secrets / Key Vault, cleartext + constant-time compare is acceptable. Flagged in Notes.
- **Endpoints added this slice:** `GET /.well-known/oauth-protected-resource`, `GET /.well-known/oauth-authorization-server`, `GET /authorize`, `POST /token`. The McpAuthenticationHandler from the SDK handles WWW-Authenticate population on 401s from `/mcp`.

Out of scope: Dynamic Client Registration, JWKS endpoint, refresh tokens, refresh token rotation, hashed client-secret storage, key rotation, token revocation, introspection, additional scopes, multi-tenancy, the `userinfo` endpoint, sign-out propagation.
