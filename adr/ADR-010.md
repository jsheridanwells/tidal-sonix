# ADR-010: `add_tracks_to_playlist` tool

Spec: [`specs/SPEC-010.md`](../specs/SPEC-010.md)

This slice closes the loop. After it lands, a single claude.ai conversation can run the full workflow:

1. `search_tracks` for each candidate song
2. Confirm matches with me
3. `find_playlist_by_name` (or `create_playlist`)
4. `add_tracks_to_playlist`

No new infrastructure — just one method on the existing `TidalPlaylistClient` and one new MCP tool. The bulk of this spec is about handling batching, rate limits, and partial-failure reporting cleanly.

Decisions:

- **Endpoint:** `POST /v2/playlists/{playlistId}/relationships/items` with a JSON:API document containing a `data` array of `{ type: "tracks", id: "..." }` refs. **Placeholder** pending Task 1's verification against the user-playlist-v2 OpenAPI spec.
- **Batch size: 20 tracks per request, configurable via `Tidal:MaxTracksPerBatch`.** Empirical-ish: TIDAL's developer forum discussions repeatedly mention 20-item batches as the practical ceiling for related operations. The configurable knob lets us tune up or down without code changes once we observe real behavior.
- **Inter-batch delay: 500 ms, configurable via `Tidal:InterBatchDelayMs`.** TIDAL's documented developer-tier rate limit appears around 2 requests per 10 seconds for catalog reads; write operations may be different (probably looser, but unconfirmed). 500 ms between sequential write batches is a conservative starting point that lets a 100-track playlist build in ~3 seconds. Tune down once we see how TIDAL actually responds.
- **Fail-fast on batch error with structured result.** The method returns an `AddTracksResult` describing how many tracks succeeded, the batch index where it failed (if any), and the error description. We do NOT attempt to rollback successfully-added tracks on a later failure — partial state in the playlist is preferable to silently dropping work that was already accepted server-side.
- **Sequential batches, not parallel.** Parallelism would multiply effective request rate and make rate-limit thrashing more likely. Sequential with inter-batch delay is correct here. If the playlist is large enough that wall-clock matters, that's a sign TIDAL's rate limit is the real constraint, not the code.
- **Append to end of playlist.** TIDAL's API likely supports positional inserts; we don't expose that to the tool. Default behavior matches what "add these tracks" naturally means.
- **No duplicate detection in this slice.** TIDAL allows duplicate tracks within a playlist. If the user has called `add_tracks_to_playlist` twice with overlapping track IDs, the playlist will contain duplicates. Mentioned in the tool description; the LLM is responsible for tracking state across calls in the same conversation if duplicate avoidance matters.
- **Tool description emphasizes provenance.** Track IDs should come from a prior `search_tracks` call where the user confirmed matches — not invented or guessed. The description states this explicitly so the LLM doesn't try to fabricate track IDs from artist/title strings.
- **Reuses everything from SPEC-009.** Same `TidalPlaylistClient`, same user-context auth handler, same token provider, same JSON:API DTOs. No DI changes.
- **`[Authorize]` on tool, same JWT scheme.**

Out of scope: removing tracks from a playlist, reordering, position-specific inserts, duplicate detection, playlist deletion, retry policies more sophisticated than fail-fast, parallel batches.
