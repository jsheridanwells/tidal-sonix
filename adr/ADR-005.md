# ADR-005: Local dev iteration via dev tunnels

Spec: [`specs/SPEC-005.md`](../specs/SPEC-005.md)

Now that the full deploy path works (SPEC-003 → SPEC-004), iteration speed becomes the bottleneck. A "change one line, see it tested by claude.ai" cycle that goes through `az acr build` → `az containerapp update` is 3–5 minutes. That'll bleed the project dry once we're iterating on tool descriptions and TIDAL behaviors. This slice codifies the alternative.

Two loops, used together:

- **Inner loop — MCP Inspector against `dotnet run`.** No claude.ai, no tunnel. `dotnet watch run` for hot reload, Inspector reconnects, edit-save-test in seconds. This is where tool *logic* iteration happens.
- **Outer loop — claude.ai against a dev tunnel pointed at `dotnet run`.** Real conversation-flow testing without redeploying. This is where tool *description, prompting, and end-to-end flow* iteration happens.

Azure deploy stays as the "milestone / commit / verify production parity" path — used after a spec is otherwise complete.

Decisions:

- **Dev Tunnels over ngrok / Cloudflare Tunnel / localtunnel.**
  - Persistent named tunnels keep the same URL forever (free), so the claude.ai connector doesn't need to be re-added on every dev session. This is the deciding factor. ngrok's free tier rotates URLs; Cloudflare requires a domain; localtunnel has the interstitial-bypass headaches.
  - The CLI is signed by Microsoft, no third-party account needed beyond a Microsoft / Entra ID / GitHub account you already have.
  - Built-in inspection URL gives you a traffic inspector akin to browser DevTools without standing anything up.
  - 30-day inactivity expiration (extendable), 10 tunnels per account — well within personal-tool needs.
- **Anonymous tunnel access.** Required: claude.ai's connector backend can't perform Microsoft auth against the tunnel. The tunnel URL becomes a secret, same trust model as the public Azure URL in SPEC-003. Don't share it. Once SPEC-006 lands, OAuth on the application gates the actual tool calls — the tunnel-URL secrecy assumption stops mattering as much.
- **Persistent named tunnel, not ephemeral.** `devtunnel create` with a chosen ID first, then `devtunnel host` to start serving. Without `create`, `host` produces a temporary tunnel with a new URL each session — kills the "URL stays stable so connector doesn't move" win.
- **Outer loop uses `dotnet run`, not the container.** The container is good for production parity (SPEC-002) but slow to rebuild. For iteration, `dotnet watch run` rebuilds on file changes in seconds. The container path is still validated end-of-spec; not needed mid-spec.
- **Two claude.ai connectors:** "TIDAL Sonics" (prod, points at the Container Apps FQDN from SPEC-004) and "TIDAL Sonics (dev)" (points at the tunnel URL). Both stay registered. You toggle whichever you need on per conversation.
- **Local port stays 3001.** Matches SPEC-002's `launchSettings.json` and SPEC-002's container port mapping. Consistency is the point.
- **MCP endpoint path stays `/mcp`.** Same as SPEC-004. The tunnel forwards the path through unchanged.

Out of scope: VS / VS Code-integrated tunnel setup (the CLI path is more portable and reproducible), automating tunnel-start as a script integrated into `dotnet run` (could be a one-line shell function later), org-restricted tunnel access (overkill for solo dev).
