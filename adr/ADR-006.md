# ADR-006: Google sign-in via OIDC federation

Spec: [`specs/SPEC-006.md`](../specs/SPEC-006.md)

This slice puts a Google-backed sign-in flow into the application without yet protecting any MCP traffic. The reason for separating it from token issuance (SPEC-007) is simple: each half is independently testable and roughly an hour, and debugging "can we authenticate the user" without the noise of "are we minting and validating JWTs correctly" is much faster than debugging both at once.

Decisions:

- **Cookie-based session auth for this slice.** The result of a successful Google sign-in is a standard ASP.NET Core auth cookie. JWTs come in SPEC-007 where they're load-bearing (claude.ai sends a Bearer token on every `/mcp` call). Cookies are the natural session mechanism for browser flows and let us test the Google federation half in isolation.
- **`AddGoogle` middleware** from `Microsoft.AspNetCore.Authentication.Google`. It's a preconfigured OIDC client for Google: ASP.NET Core knows Google's authorization and token endpoints, and the package handles state, PKCE, and token exchange. We write essentially zero OIDC code.
- **Email allow-list of one, enforced in the OAuth callback.** The allow-list check happens in `Events.OnTicketReceived` on the Google handler. If the email isn't in the list, we redirect to `/access-denied` and call `HandleResponse()` to stop the default sign-in flow. Cookie is never issued.
- **Secrets via `dotnet user-secrets` locally.** ClientId, ClientSecret, and the allow-list all go in user-secrets — none of them belong in the repo. Production secrets move to Key Vault in SPEC-010; this slice doesn't deal with production at all.
- **Google OAuth client in "Testing" mode with you as a test user.** No app verification required for the `openid email profile` scopes we're using. 100 test user limit; we use one. Tokens issued in testing mode have shorter refresh-token lifetimes, but our cookie session doesn't depend on Google refresh tokens — once signed in, the cookie carries the session.
- **Three redirect URIs registered with Google up front:** `http://localhost:3001/signin-google`, `https://<tunnel-id>-3001.<region>.devtunnels.ms/signin-google`, and `https://<app-fqdn>/signin-google`. Google allows multiple redirect URIs per client; registering all three now means SPEC-007 and beyond don't get blocked on "go back to Google Cloud Console and add another URI."
- **`/me` as the verification endpoint.** Returns JSON identity claims if signed in, 401 otherwise. Hand-rolled rather than `[Authorize]`-decorated; the default-scheme dance gets cleaner once SPEC-007 introduces JWT alongside cookies, so deferring `[Authorize]` until then keeps this slice's auth wiring single-purpose.
- **No changes to `/mcp`.** Authentication on `/mcp` lands in SPEC-007. This slice adds a parallel sign-in subsystem; existing MCP traffic stays unauthenticated. Inspector and both claude.ai connectors (prod and dev) keep working exactly as they did at the end of SPEC-005.
- **Endpoints added this slice:** `GET /signin`, `GET /signout`, `GET /me`, `GET /access-denied`. The Google callback path `/signin-google` is handled by `AddGoogle` middleware — no controller needed.

Out of scope: JWT issuance, `/.well-known` metadata endpoints, `/authorize` and `/token` endpoints, `[Authorize]` on tools, claude.ai connector changes, refresh tokens, sign-out propagation to Google, multiple users / role claims, HTTPS enforcement on the local dev server (Google special-cases `http://localhost` for redirect URIs).
